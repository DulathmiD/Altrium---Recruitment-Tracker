# Activity Diagram corrections — checked against the real system

All 18 pages in `Activity Diagrams.drawio.xml` read and checked directly against the actual backend/frontend code. The Use Case file (`USE CASE 2.drawio.xml`) is still unreadable — its diagram content is compressed inside the XML (same problem as the `.html` exports), so re-export it with compression off (draw.io: File > Properties > uncheck "Compressed") and re-upload, or send screenshots.

## Systemic issues (appear across multiple diagrams)

1. **"Navigate to vacancy list → Select target vacancy → View candidate list" is the wrong entry point, and it's repeated in six diagrams** (Upload CVs, Screen CVs, Shortlist CVs, View all vacancy candidates, Recommend candidate). Checked `VacanciesPage.tsx` directly — there is no click-through from a vacancy into its candidates anywhere in the code. The real Candidates page is a flat list across every vacancy with Vacancy as one optional filter among several (Search, Vacancy, Stage, Status, Min Score), defaulting to "ALL." Fix all six: replace with "Navigate to Candidates page → (optionally) filter by vacancy."

2. **"Screen CVs" and "Shortlist CVs" are two different diagrams describing the same real action, and they contradict each other.** One calls the decision "Minimum requirements met?", the other calls it "Candidate moves forward?" — there's only one real decision point (shortlist or reject via the `stage` field). Recommend merging these into one diagram, or deleting one, rather than keeping two diverging descriptions of the same action.

3. **"Recommend candidate" and "Recommend progression stage" are two different diagrams describing the same real action (`submitStageRecommendation`), and they actively conflict.** "Recommend candidate" frames it as "Recommend for hire? → Approve/Reject." "Recommend progression stage" frames it as "Advance to next stage? → advance / not progressing." Neither wording matches the real UI/enum exactly, but "Recommend progression stage" is much closer. Real values: `RecommendationValue` enum is `ADVANCE` / `DO_NOT_PROGRESS`, and the UI shows "Proceed / Do Not Proceed" at every round except the final one, where it's "Hire / Reject" instead. "Approve"/"Reject" as generic labels don't match either case. Fix: pick one diagram, and if it needs to show both non-final and final rounds, branch on "is this the final round?" first, then show Proceed/Do Not Proceed vs Hire/Reject as the two different label sets — don't use "Approve."

## Per-diagram findings

**Log in / Authenticate user** — real, confident bug: these two diagrams show three different error messages for three different login failures ("User not found," "Invalid credentials," and an implied deactivated-account message from the "User active, role assigned?" branch). The real backend (`auth.controller.ts`) deliberately returns the exact same generic message — "Invalid email or password" — for a wrong password, a nonexistent email, AND a deactivated account, specifically so the failure reason can't be inferred from the response (this was independently confirmed earlier when auditing your Sprint 1 submission doc's test cases, which had the same wrong assumption). Collapse all three failure paths in both diagrams to one identical error message. Also: "role assigned?" isn't a real state — `User.role` is required at account creation, there's no "no role" case to branch on; drop that half of the condition, keep just the active/inactive check.

**Manage vacancies** — "Archive vacancy and retain candidate records" uses the wrong verb. The real status is `CLOSED` (enum: OPEN/CLOSED/ON_HOLD), not "archived" — there's no archive state or table anywhere in the schema. "Retain candidate records" is correct (confirmed — no cascade delete on vacancy closure). Rename the box to "Close vacancy (candidate records retained)."

**Upload CVs** — missing the entire review step, not a small gap. The real flow is upload → the system auto-extracts name/email/phone from each CV → HR reviews and can edit every extracted field before confirming → only then is it saved. Your diagram goes straight from "Submit upload" to "All files valid? → Store CV in centralized database," skipping the extraction-review screen entirely. Also missing: duplicate-candidate detection (if an uploaded CV's email matches an existing candidate, the system flags the match and re-applies them to the new vacancy instead of silently creating a duplicate — a deliberate "warn, don't block" design). Add both steps between "Submit upload" and "Store in database."

**Screen CVs** (also applies to "Shortlist CVs," same structure) —
- "System records last reviewed CV status (reviewer and timestamp)" is sequenced after the Shortlist/Reject decision. In the real system this stamp is written the moment HR clicks "View CV" — a separate, deliberate action — and happens *before* the decision, not after. Move that box earlier, right after the CV-review step.
- "Rejected CV gets archived" — same wrong "archived" language as above, and it's worse here: there's no archive at all, rejecting just sets `stage: REJECTED`. It's also not a dead end — a "Reconsider" action exists specifically to un-reject a CV-stage-rejected application, so nothing here is ever really "archived" in the permanent sense the word implies.
- "Shortlisted/Rejected CVs moved to separate section" (Shortlist CVs version) overstates it slightly — they're not moved to a different page/section, they're the same list with a different status badge and an optional Status filter (Unreviewed/Active/Rejected). Minor wording fix, not a functional error.

**Assign Interviewer** — real mismatch on where the availability check belongs. This diagram checks "Interviewer available?" (implying a calendar/schedule check) before assigning someone to a vacancy. In the real system, assigning an interviewer to a vacancy (`VacancyInterviewer`) is just adding them to an eligible-panelist pool — there is no availability check at that point. The actual double-booking/conflict check happens later, at the *scheduling* step (`scheduleInterview` returns a 409 if the same person is booked at the same time). This diagram is describing scheduling-time logic under the wrong activity. Either remove the availability check here, or move it into "Schedule interview" where it actually happens.

**Schedule interview** — incomplete relative to the real form. Missing: selecting which interview round/stage this slot is for, selecting a panel (from the vacancy's assigned pool, or a saved named panel — the real form has a panel checklist, not a separate "assign interviewer" sub-call), the scheduling-conflict check (409 on double-booking), and the fact that one slot can hold multiple candidates added afterward (the `InterviewSlot`/`Interview` split — a slot is the calendar entry, `Interview` rows are added per candidate, potentially several to one slot). Also missing the server-side gate that the candidate must already be `SHORTLISTED` before they can be scheduled.

**View all vacancy candidates** — same wrong vacancy-first entry point as above (see systemic issue #1). Also, the filter box says "status (selected/rejected)" — the real Status filter values are "Unreviewed / Active / Rejected," not "selected." ("Active" is a broader bucket covering both Shortlisted and Hired.) Once you fix the entry point, Vacancy itself should become one of the optional filters listed here (alongside Stage, Status, Min Score, Search), not a forced step before the list even loads.

**View interview schedule** — worth double-checking against the actual screen before trusting this one. The real Interviewer/Management "My Interviews" pages are a month-based calendar (click a day to see that day's slots), not a list with a "select a date range" filter form. If the real screen doesn't have a distinct date-range picker separate from calendar navigation, this diagram's "Date range selected?" branch needs to become "navigate to a different month/day" instead.

**View applicant profile** — mostly fine as a high-level abstraction, but incomplete: the real Candidate Detail page also has Review Notes (editable), Hiring Manager assignment, Upcoming/Completed Interviews, and Email History, not just "profile, CV, and application history." Not wrong, just thinner than the real page — expand if this needs to be a faithful diagram rather than a summary.

**Record interview feedback** — the most significant error found in the whole set. This diagram gates the flow on "is user a hiring manager?" and has HMs entering a recommendation as part of submitting feedback. That's not how the system works at all: Hiring Managers do not submit interview feedback — they were explicitly removed from the panelist/feedback flow (an earlier design reversal removed HM's "My Interviews" page entirely, specifically because HMs don't sit on panels). Feedback (score + comments) is submitted only by Interviewers and Management when they're on the panel. The Hiring Manager's recommendation is a completely separate action, already correctly covered by its own diagram ("Recommend progression stage"). Remove the "is user a hiring manager?" branch and the "Enter recommendation" step from this diagram entirely — it should end at "Submit feedback → Feedback recorded" for every user who reaches it.

**update interview feedback** — the ownership check ("is user the original author of feedback?") is correct and matches the real code exactly. One missing required step: the real edit form requires a non-empty **reason for the change** before it can be submitted — add an "Enter reason for change" box between "Edit feedback fields" and "Submit updated feedback." Without a reason, the real system rejects the request.

**Record feedback modifications** — mostly accurate (previous value, new value, editor identity, timestamp all match the real `FeedbackAuditLog` table). Two fixes: add "capture reason for change" as one of the captured fields (it's stored alongside the before/after values, and it's required). Also, "store modification record in audit trail" should specify this is a dedicated feedback-history table, not the general system Audit Log — they're deliberately two separate tables in the real schema, and conflating them is a real distinction worth keeping precise for the viva.

**Recommend candidate** — see systemic issue #3 above; also has the same wrong vacancy-first entry point as issue #1.

**Recommend progression stage** — closest to accurate of the two recommendation diagrams, but "Select next interview stage" as a manual action is wrong. The Hiring Manager never picks which stage to advance to — the system automatically moves the candidate to the vacancy's next configured round in order, with no skipping allowed. Remove that box; "advance" should go straight to "Submit progression recommendation."

**Review Recruitment Dashboard** — can't fully verify without knowing which role's dashboard this represents (the diagram doesn't say). If this is meant to be general, it isn't — Management's dashboard is auto-scoped to their own department (not user-filterable), and a filter by "score" isn't something I can confirm exists on any dashboard. Worth specifying which dashboard this is (Management / Leadership / Hiring Manager) since their filter options genuinely differ, and double-checking the "score" filter is real before keeping it.

**Review recruitment reports** — matches Management's per-vacancy PDF report correctly (real, built, PDF-only — no Excel option, in case that ever gets added back in). But it only covers a single vacancy's report. If this diagram is meant to also represent Leadership's four organization-wide/department-wide report PDFs, that path is missing entirely — those aren't reached by "select a particular vacancy" at all.

# Use Case Diagram corrections

Received as an image, checked against the same code.

**"Recommend candidate" (Recruitment and Approval) and "Recommend interview stage progression" (Interview Management) are almost certainly the same real action modeled twice.** There is exactly one recommendation mechanism in the backend — `submitStageRecommendation`, one Hiring Manager action, one `StageRecommendation` row per call. This is the identical duplication problem already flagged in the Activity Diagrams ("Recommend candidate" vs. "Recommend progression stage" there too) — it isn't a coincidence, it's the same underlying confusion carried into both diagram sets. Pick one use case, put it in one package, and delete the other.

**If "Approve/Reject applicants" is attached to Management rather than Hiring Manager, that's backwards.** Management does not approve or reject candidates anywhere in the real system — that decision-making role belongs entirely to the Hiring Manager (Pending Decisions: Proceed/Do Not Proceed per round, Hire/Reject at the final round). Management's real actions are department-scoped dashboard/report viewing, not candidate decisions. Double-check which actor's line actually connects to that oval — if it's Management, move it to Hiring Manager.

**"Approve/Reject" is also the wrong label regardless of actor.** The real decision has two different label pairs depending on where the candidate is: "Proceed / Do Not Proceed" at every round except the last, "Hire / Reject" only at the final round. Nothing in the real system is ever literally labeled "Approve."

**Missing IT Admin use cases.** The Administration package only shows Manage user accounts, Maintain audit logs, Assign user roles, Monitor performance. Two real, built, IT-Admin-only features aren't represented at all: configuring notification templates (the editable email text behind automatic sends) and managing system backups (real scheduled + on-demand `mysqldump`, with its own status page). Add both.

**Missing: viewing feedback edit history.** "Record feedback modifications" only covers the backend recording side (writing the before/after/reason to the audit table). There's no use case for anyone actually *viewing* that history — but that's a real, working feature: Hiring Managers can view it on their decision screens, and an Interviewer/Management panelist can view their own edit history on their own Feedback screen. Worth adding as its own use case if this diagram is meant to reflect what's actually viewable, not just what's recorded.

**"Upload CVs" → includes → "Screen CVs" → includes → "Shortlist CVs" uses `<<include>>` incorrectly.** `<<include>>` means the base use case *always* triggers the included one as part of the same execution. Uploading a CV doesn't always immediately trigger screening it — HR uploads now, and typically screens/shortlists it separately, later, when working through the Candidates list. These should probably be three independent use cases with no `<<include>>` relationship between them, not a forced chain.

**"Monitor recruitment performance" (Recruitment and Approval) and "Monitor performance" (Administration) are two real, different features — but the names are too close.** One is recruitment KPIs (Leadership/Management dashboards), the other is system health (IT Admin's Systems page: server load, response time, concurrent users). Not an error, but worth renaming one of them (e.g. "Monitor system performance" for the IT Admin one) so they don't read as duplicates at a glance.
